Design before you build

Two ideas run through this page. First: good design is a process, not a talent, and the double diamond is the process: open up, narrow down, open up, narrow down. Second: every screen has a UI half (what you see) and a UX half (how it works and feels), and the exam wants you to stop swapping them. The code comes on the next page. This one is about not building the wrong thing.

The deal. You have been scoring about 10 out of 15. This page is out of 30, and the honest target is 21 on the first pass and 26 on the second. Marks only count if you write your answer before opening the mark scheme — otherwise you're just reading, and reading feels like learning without being learning. The Problem Lab near the bottom is extra: no marks, nothing to lose, and the place where the hard-question habit gets built.

    Five traps

    Read before any test

    Drawing the double diamond as a straight line

    The sentence you write: "First you discover, then define, then develop, then deliver, and it's finished."

    Why it loses the mark: it hides the thing the shape is for. Each diamond opens up and then narrows, and a test result can send the team back to an earlier phase if it shows they solved the wrong problem.

    Write instead: "Two diamonds, each diverging then converging: the first finds the right problem, the second builds the right solution, and testing can send you back."

    Putting ideas in Define

    The sentence you write: "In Define the team comes up with lots of ideas."

    Why it loses the mark: Define narrows. It ends with one problem statement. Lots of ideas is Develop, the second diamond opening up. Students swap the two because both start with D and both sound like making things.

    Write instead: "Define converges on one clear problem statement; ideas are generated later, in Develop."

    Swapping UI and UX

    The sentence you write: "UX is how the app looks and UI is how it works."

    Why it loses the mark: it is backwards, and examiners see it constantly. UI is what you see and touch: colour, type, buttons, icons. UX is how the whole thing works and feels: how many taps, whether it tells you what happened, whether you can find things.

    Write instead: "UI is the visual interface; UX is the overall experience of using it, including how easy it is." A quick test: if the fix changes how a screen looks, it is UI; if it changes how the task goes, it is UX.

    Using colour as the only signal

    The sentence you write: "Errors are shown in red, so users can see them."

    Why it loses the mark: some users cannot tell red from green (roughly 1 in 12 men), screens get washed out in sunlight, and screen readers do not see colour at all. A signal that depends on colour alone fails all of them.

    Write instead: "Errors are shown in red and with an icon and a text message saying what to fix."

    Polishing the wireframe too early

    The sentence you write: "I made the wireframe look nice with the real colours and photos so the client would be impressed."

    Why it loses the mark: a polished draft makes people argue about the colour of a button when the problem is that the page has no button. Grey boxes and labels keep everyone looking at structure, and they take minutes to change.

    Write instead: "A low-fidelity wireframe uses plain boxes and labels so feedback is about layout and flow, not decoration."

    The four test papers

    30 marks each

    These are the printed papers that go with this page. Do them on paper, timed, with your phone in another room: no calculator, and no Figma, because every screen you need is printed on the paper. Medium first; only move to the hard papers once you're clearing 21 on a medium one.

     BPaper B — Medium35 min
